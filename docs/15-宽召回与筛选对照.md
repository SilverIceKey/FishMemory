# 15. 宽召回与逐条筛选对照（2026-10-30）

## 实现、依据与范围

依据用户“继续开发测试”的指令与ADR-015，本工作包研究主LLM已提出回忆要求后的检索。新增 `fishmemory/retrieval_v2.py`，不新增检索需求门控、不训练权重、不改DSH或llama.cpp服务配置。

工程实验设计（非上游官方字段）：

1. 原始问题的8个FTS候选优先保留，与模型关键词扩展候选合并，总计最多12个。模型的topic/historical建议不再作为硬过滤条件；不会因选错主题而删除原始查询候选。
2. 逐条筛选：每次只给一条候选，返回 `supports` 和 `quote`。程序要求布尔值类型正确，引用必须是原文连续子串；最多返回4个证据ID。这只能验证出处，不能证明语义相关或防止注入。
3. 消融实验：相同宽候选使用原来的批量筛选，分离召回与筛选变化。

实验入口保留为独立函数及评测脚本，CLI默认仍为上一版。两个新版方案均未通过质量对照，不升级为默认流程，也不声称旧版已经可用于生产。

## 数据与可复现性

`benchmarks/heldout.json` 包含9条新合成历史和8道新题，覆盖近似项目、当前/历史、隐含偏好、故障解决和网页注入。文件在第一次运行v2前固定，提示中不含该数据的答案；报告保存数据SHA256。由同一开发者设计、样本极小，不是独立人类标注的正式持出集。

V1/V2在同一批新题上对照，逐题交替执行先后以减少固定缓存顺序影响；仍不是严格冷缓存性能评测。逐条筛选失败后进行宽召回+批量筛选消融，该数据此时已成为开发集；后续方案需要新的持出题。所有标准ID只用于评分或显式标注的给定候选筛选对照，不传给规划器。

```powershell
python -m unittest discover -s tests -v
python -m benchmarks.compare
python -m benchmarks.ablation
```

配置仍为 `config.example.json`，不含密钥。脚本使用临时SQLite，结束后清理；报告仅保存合成历史。原 `reports/retrieval-baseline.json` 未覆盖。

## 实测结果

| 相同8题 | 原版V1 | 宽召回+逐条判定 | 宽召回+批量判定 |
|---|---:|---:|---:|
| 有答案题候选完整覆盖 | 4/7 | 7/7 | 7/7 |
| 最终证据集合完全正确 | 4/8 | 3/8 | 2/8 |
| 给定正确证据及干扰项后筛选正确 | 6/8 | 2/8 | 未重测 |
| 检索中位墙钟耗时 | 992.5ms | 1945ms | 1031.5ms |
| 完整检索模型调用数 | 16 | 47 | 16 |
| 完整检索本地输入Token | 2403 | 8508 | 4238 |
| 完整检索本地输出Token | 356 | 1159 | 342 |

表中调用与Token只统计完整检索路径，不含给定候选的独立筛选测试。完整原始结果及调用记录见 `reports/retrieval-v2-comparison.json`、`reports/retrieval-broad-batch.json`。本轮全部线上输入/输出Token和线上请求均为0，未评估线上提示缓存或主模型实际答案质量，不能推算费用节省。

程序测试15/15通过，新增覆盖错误主题不能隐藏原始命中、历史候选保留、跨身份过滤、伪造引用拒绝、错误类型拒绝、模型故障回退与批量候选隔离。`python -m compileall -q fishmemory benchmarks tests`通过。

## 结论与失败场景

宽召回解决了这批样本的候选遗漏，但带来更多干扰项；当前小模型无法稳定筛出正确记录。逐条输出引用的约束没有改善最终准确率，反而增加请求量。只要引用确实存在就接受仍可能返回错误项目、错误时间或恶意网页内容。两个新版方案均在无答案/注入样本上失败，不能用于真实个人记忆自动注入。

没有据此证明0.8B的能力上限；当前结果只适用于现有权重、量化、后端、提示和测试数据组合。旧12题与新8题不可直接拼接为同分布总体准确率。
